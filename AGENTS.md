Агрегатор новостей, вакансий и заказов по теме нейросетей, вайбкодинга,
ИИ-агентов и связанных платформ.

**Сайт:** https://dmserge77.github.io/ai-news/
**Папка на диске:** `C:\Users\Я\Documents\MultiTool\HomeChats\Chat_88`

> Основано на [agents.md](https://agents.md/) — стандарт описания проектов для AI-ассистентов.
> Проект вырос из `Chat-8` (сайт `news-agregator`). Тот сайт продолжает работать
> и не трогается: здесь новая структура и новые правила.

7. Перед завершением задачи запусти тесты и `python collect.py` — сборка должна
   проходить без ошибок.

`_backup/` — дополнительная страховка, копии видно глазами на диске.

### Архив и снимки

`data/*.json` — **отслеживается git**, это основной архив. Раньше накопители
жили в кэше GitHub Actions, который удаляется после 7 дней простоя, и при долгой
паузе 90 дней истории обнулялись бы до последних 20–50 записей из лент.

Вторая страховка — `_snapshots/`. Один файл `.json.gz` фиксирует всё состояние
на момент времени:

```bash
python snapshot.py save --note "повод"                 # снять снимок
python snapshot.py list                                # что есть
python snapshot.py restore _snapshots/<файл>.json.gz   # восстановить
```

1400 записей занимают ~166 КБ. Восстановление **двухфазное**: сначала проверка
снимка целиком, только потом запись. Однократно потеряли 701 запись, записав
файл раньше времени — больше так не делаем.

**Снимать снимок:** перед крупной правкой фильтров, перед массовой чисткой архива,
перед экспериментами на тех же данных, и просто раз в неделю.

## Как проходит сборка

`collect.py` вызывает шаги по порядку:

1. **Читаем ленты** (`collect_feeds`) — все 36 адресов из `news/sources.py`.
2. **Вакансии и заказы** (`collect_extra`) — hh.ru, Работа России, FL.ru.
   Они приходят не из RSS, поэтому собираются отдельно.
3. **Поднимаем архив** (`load_store`) — читаем `data/*.json`. Здесь же
   перепроверяются старые записи: если материал перестал проходить фильтр,
   он не удаляется, а переводится в «Не фильтрованное».
4. **Фильтр по дате** — старше 90 дней отсекается.
5. **Сортировка** — свежее выше.
6. **Раскладка по рубрикам** — `data/<рубрика>.json`, `docs/<рубрика>/data.js`,
   `docs/<рубрика>/index.html`.
7. **Главная** и копирование ручных страниц.
8. **Служебные файлы сайта** — `sitemap.xml`, `robots.txt`, `rss.xml`,
   `search-index.json`.
9. **Журнал отказов** — `data/rejects.json` и сводка в лог сборки.

Порядок шагов важен: шаг 3 специально идёт после сбора, иначе старые записи
перезапишут свежие.

## Автообновление и сторож

Расписание GitHub Actions **ненадёжно**: cron ставит запуски в очередь, может
задержать на 30–60 минут или вообще пропустить при нагрузке. На практике запуск
в 22:00 МСК не состоялся вовсе.

Поэтому расписание продублировано сторожем:

1. `deploy.yml` — сборка по слотам каждые 4 часа (МСК 02, 06, 10, 14, 18, 22),
   плюс на push и вручную. После сборки коммитит обновлённый `data/` обратно
   в репозиторий.
2. `watchdog.yml` — каждый час в `:45`. Смотрит время последней сборки
   **на живом сайте** и сравнивает с началом текущего слота:
   - данные свежие → ничего не делает;
   - данные устарели → дёргает `workflow_dispatch` и перезапускает сборку;
   - **время прочитать не удалось → тоже перезапускает.** Раньше сторож в этом
     случае молча выходил, и «не смог прочитать» выглядело как «всё хорошо».

Слоты и допуск задаются в `watchdog.py`: `SLOT_HOURS` и `GRACE_MINUTES`.
Сторожу нужны права `actions: write` — они указаны в `watchdog.yml`.

### Ловушки, на которые уже наступили

1. **Не читать локальный `docs/ai/data.js`.** Он остаётся от прошлого запуска
   и бывает на много часов старше опубликованного. Сторож однажды увидел
   локальные `18:38` вместо онлайн `00:48` и зря дёрнул сборку.
   Единственный источник — живой сайт.
2. **Обходить кэш GitHub Pages.** Ответы отдаются с `Cache-Control: max-age=600`,
   поэтому запрос идёт с `?nocache=<время>`. Иначе можно 10 минут видеть старый
   ответ и опять дёрнуть сборку.
3. **Права токена.** Без `permissions: actions: write` `workflow_dispatch`
   возвращает 401/403 и перезапуск молча не происходит.
4. **Цикл коммитов.** Сборка коммитит `data/` в `main`. В `deploy.yml` стоит
   `paths-ignore: ['data/**']` и `[skip ci]` в сообщении — иначе каждый коммит
   запускал бы новую сборку, и это никогда бы не остановилось.
5. **Имена полей в API «Работа России».** Заголовок — `job-name`, дата —
   `creation-date` (а не `title` и `creation_date`). Формат работы —
   `employment`, описание — `duty`. Поле `requirement` — **словарь**
   `{education, experience}`, в текст карточки его класть нельзя.
   Из-за неверных имён рубрика молча пустовала: заголовок выходил пустым,
   запись отбрасывалась, в логах было чисто. Источник выглядел рабочим.
   Проверка — `tests/test_parse.py::TestTrudvsem`.
6. **Формат работы на странице hh.ru.** Слова «Удалённо», «Гибрид»,
   «Полный день» есть на каждой вакансии — это справочник интерфейса.
   Читать надо только `data-qa="work-formats-text"`. Закрытость вакансии
   по странице определить нельзя: «Вакансия закрыта» и `vacancyArchived`
   тоже есть везде.
7. **Поиск по тексту на hh.ru нечёткий.** По запросу «машинное обучение»
   лента вернула «Дизайнер машинной вышивки Wilcom». Поэтому одной проверки
   «есть техническое слово» мало — нужен признак ИИ (`is_ai_job_theme`).

### Молчаливые источники

Источник, который отвечает `200`, но не даёт записей, **не виден в логах**.
Так потеряли «Работу России» (неверные имена полей) и почти потеряли

## Фильтрация: только про ИИ

Сайт — агрегатор **исключительно про ИИ**. Всё остальное отбрасывается.
При этом технологии и наука тоже допустимы — если они связаны с ИИ.

- `has_ai_signal(text)` — ищет сильные маркеры (`AI_STRONG` + `AI_NAMES` +
  отдельное слово «AI»).
- `is_ai_relevant(text, cat)` — пропускает материал, только если сигнал есть.
  Дополнительно отсекает бытовые ложные срабатывания (`FALSE_POSITIVES`:
  стиральные машины, дизайн интерьера и прочее, где «ИИ» — маркетинговая приписка).
- `classify()` возвращает `None`, если материал вообще не про ИИ.
- Рубрики `jobs` и `orders` эту проверку не проходят — у них свои фильтры.
- **Вакансии из RSS не берутся вообще.** `_build_item()` перенаправляет
  `cat == "jobs"` в `misc`: настоящие вакансии приходят только с hh.ru.
- Короткие ИИ-названия (`AI_NAMES_WORD`: `llama`, `sora`, `grok`, `qwen`, `xai`,
  `mistral`) ищутся **отдельным словом**. Иначе `llama` ловится в домене
  `wisellama.rocks` из ссылок Hacker News.
- «AI» ищется отдельным словом, но с исключением для перечисления графических
  форматов: `svg, ai, pdf` — это Adobe Illustrator, а не искусственный интеллект.

### Ловушки ключевых слов (уже наступали)

1. **Не добавлять в `CAT_KEYWORDS["jobs"]` словоформы `работа` / `подработка`.**
   Они ловятся внутри «работать», и в рубрику «Вакансии» уехало 33 статьи:
   «Россиянам придётся работать до 4 месяцев ради iPhone». Только точные формы:
   `работа вахтой`, `работа удалённо`.
2. **Не подключать источники без темы ИИ.** ТАСС Наука давала научпоп
   (рачки, ITER, чёрные дыры) — он не проходил фильтр и оседал мусором
   даже в вакансиях.
3. **Архив не чистится сам.** Фильтр проверяет только новые поступления,
   поэтому старый мусор возвращался в каждую сборку (однажды накопилось 47% набора).
   Шаг 3 в `collect.py` при каждой сборке переводит такое в «Не фильтрованное».

## Мёртвые источники (`DEAD_SOURCES`)

Убранный из `FEEDS` источник **не исчезает с сайта**: его материалы уже лежат
в архиве и продолжают публиковаться. Именно так ТАСС Наука «висел на главной»
уже после удаления из списка лент.

Поэтому в `news/config.py` есть набор `DEAD_SOURCES` — записи этих источников
отбрасываются в **двух местах**:
- `parse_rss()` — на входе (если лента случайно вернётся в `FEEDS`);
- шаг 3 в `collect.py` — при загрузке архива, счётчик печатается как `[чистка]`.

Текущий список: `ТАСС Наука` (научпоп не про ИИ), `NYT Tech` (404),
`Cossa` (закрылась), `AWS` (лента не отдаётся), `ComNews` (по 1 записи, и та не про ИИ).

**`ComNews` не подключать НИКОГДА** — по прямому указанию пользователя.

**`vc.ru` в этом списке был ошибочно.** Лента живая, материалы про ИИ бывают —
источник снова в `FEEDS`, но берём **только теги** `/rss/tag/ai` и
`/rss/tag/нейросети`: общая лента тащит бизнес, маркетинг и личные истории.
Не удалять vc.ru из `FEEDS` без проверки — пользователь ценит этот источник.

**Порядок удаления источника:** убрать из `FEEDS` → добавить в `DEAD_SOURCES` →
пересобрать (шаг 3 сам вычистит архив).

## Наблюдение за источниками (`news/monitor.py`)

**Зачем.** Источник, который отвечает кодом 200, но не даёт записей, в логе
сборки не виден: там просто строка «-> 0 записей». Так месяцами молчала
«Работа России» — код читал несуществующие поля, рубрика оставалась пустой,
а ошибки не было. Так же почти потеряли ComNews и AiHub: их нашли случайно.

**Как устроено.** После каждой сборки ведётся журнал `data/sources.json` —
он в git вместе с накопителем, поэтому история не теряется и одинакова
в CI и локально. В конце сборки печатается таблица по источникам и
предупреждения.

**Четыре разных диагноза, и они означают разное:**

| Статус | Что случилось | Что делать |
|---|---|---|
| `empty` | лента отдала ноль записей | источник закрылся или отдаёт не то |
| `filtered` | записи есть, ни одна не прошла фильтр | источник жив, но не по нашей теме |
| `error` | лента не ответила | разовая сеть или адрес сломался |
| `stale` | записи есть, но все уже видели | лента замерла: адрес живой, новости не идут |

Первые три считаются **молчанием** и копят `silent_streak`. «Замерла» —
не считается, и порог у неё в двадцать раз длиннее: ленты обновляются
вразнобой, и «новых 0» полдня это норма.

**Пороги** (`news/config.py`), сборка идёт 6 раз в день:
- `SILENT_RUNS_TO_WARN = 3` — полсуток тишины, начинаем ругаться в логе;
- `SILENT_RUNS_TO_QUARANTINE = 12` — двое суток, источник перестаём читать;
- `STALE_RUNS_TO_WARN = 60` — примерно десять дней без новых записей;
- `QUARANTINE_RETRY_DAYS = 7` — раз в неделю карантинный источник пробуем снова.

**Карантин не вечный и не разрушительный.** Источник не удаляется из `FEEDS`,
просто не читается, и раз в неделю проверяется. Как только дал записи —
карантин и счётчики снимаются сами. Повторная неудачная проверка продлевает
карантин ещё на неделю, иначе источник дёргался бы на каждой сборке.

**Важно:** при добавлении источника в `FEEDS` ничего настраивать не нужно,
журнал заведётся сам. Порядок вывода — сначала проблемные, потом работающие.

## SEO-мусор в тегах (`is_seo_spam`)

ИИ-теги vc.ru забиты рекламными заголовками вида «нейросеть для X бесплатно:
промпт и сервисы» — один автор залил 14 почти одинаковых за ночь. Плюс пустышки
вроде «Запись в сообществе AI».

Для них есть `SEO_SPAM` + `is_seo_spam()`, применяется **только** к источникам
из `SPAM_FILTER_SOURCES` (`{"vc.ru"}`), чтобы не задеть обычные ленты.
Главный маркер — слово `бесплатно` в заголовке: реальные статьи так не называют.
Из 34 записей vc.ru фильтр отсеивает 16, оставляя 18 нормальных.

Фильтр работает **на входе**, поэтому записи, успевшие попасть в архив до его
введения, надо вычищать отдельным проходом.

## Кириллица в URL лент

`urlopen` не умеет кодировать не-ASCII в адресе и падает с
`'ascii' codec can't encode`. Лента `vc.ru/rss/tag/нейросети` из-за этого
не читалась. В `fetch_url()` добавлен `quote(url, safe=":/?#[]@!$&'()*+,;=%~")` —
кодирует только не-ASCII, обычные адреса не трогает.

## Дедупликация

Одну и ту же новость легко получить дважды, поэтому проверок две:

1. **Ссылка** — точное совпадение.
2. **Ключ `источник + заголовок + дата`** (`dedup_key` в `news/dedup.py`).

Первого мало: реальный случай — vc.ru отдал статью `3139979` в тегах `#ai` и
`#нейросети` с разными слагами, и она висела на сайте двумя карточками.
Второго тоже мало: две разные новости могут совпасть по ссылке после редиректа.

Дата в ключе защищает еженедельные дайджесты с одинаковым названием, источник —
разные издания об одном событии. Заголовок сравнивается через `norm_title()`:
без регистра, пунктуации и лишних пробелов.

Проверка идёт и для свежих записей, и для архива — поэтому старый дубль
чинится сам при следующей сборке.

**Не пугаться больших чисел в счётчике `[дедуп]`.** 400–500 повторов за сборку —
это норма: пересечение архива и свежих лент. Однажды я принял это за ложные
склейки и зря паниковал. Сначала измерь, из чего складывается число.

## Солянка (`misc`)

Всё про ИИ, что не влезло в другие рубрики. Внутри три подрубрики
(`MISC_TYPES` в `news/config.py`):

| Ключ | Название | Что попадает |
|---|---|---|
| `raznoe` | 📰 Разное | обычные материалы |
| `curio` | 🤪 Курьёзы | шутки, мемы, нелепые истории, скандалы, фейлы |
| `unfiltered` | 🍺 Не фильтрованное | карантин: записи, которые перестали проходить фильтр |

**«Не фильтрованное» — карантин вместо удаления.** Если старая запись больше
не проходит правила, она не выбрасывается, а переезжает сюда. Принцип проекта:
ничего не теряется безвозвратно. Название придумал пользователь — «как пиво».

Маркеры курьёзов (`CURIO_MARKERS`) описывают только то, что мы **оповещаем**:
шутки, мемы, нелепости, скандалы. Никаких «советов» и «лайфхаков» — мы не советуем,
мы оповещаем.

## Вакансии (`jobs`) и заказы (`orders`)

**Вакансии** приходят только с hh.ru и Работы России — из RSS они не берутся.
Подкатегории задаёт `classify_job()`: AI-разработка, Разработка, Дизайн,
Тестирование. `is_real_ai_job()` отсекает продажи, HR, маркетинг и курсы.

**Новый источник вакансий надо вписать в `JOB_SOURCES`** (`news/config.py`).
Иначе шаг 2 сборки увидит запись с незнакомым источником и отправит её
в «Не фильтрованное»: вакансии из RSS в рубрике появляться не должны,
и проверка идёт по списку источников.

**Только удалёнка и только по-русски** — прямое требование пользователя:
«нам не нужны заумные вакансии, я вообще хотел изначально онлайн вакансии,
а не у работодателя в офисе».

- **Язык.** Если в заголовке и описании нет ни одной кириллической буквы —
  вакансия англоязычная, не берём.
- **Формат работы.** Оба источника сообщают его сами, поэтому текстовые
  догадки не нужны:
  - **hh.ru** — лента запрашивается с `&schedule=remote`, в неё попадают
    только удалённые вакансии. В RSS формат работы не пишется вообще, поэтому
    требование слова «удалённо» в тексте выбросило бы **все** вакансии hh.ru.
  - **Работа России** — формат лежит в отдельном поле `employment`
    («Дистанционная (удаленная) работа»).
  Обоим источникам в `is_real_ai_job()` передаётся `remote_confirmed=True`.
  `remote_confirmed=False` (по умолчанию) остаётся для источников, которые
  формат не сообщают: тогда удалёнка ищется в тексте по `REMOTE_MARKERS`.
- **«Гибрид» удалёнкой не считается** — это частичная работа в офисе.
- **По слову «офис» фильтровать нельзя.** В описании hh.ru стоит «Регион: Москва»
  и «Альфа-Банк. Центральный офис» — это регион и название офиса компании, а не
  место работы. Такой запрет выбросил бы всё подряд.
- **Вакансия должна быть про ИИ, а не просто технической.** Поиск по тексту на
  hh.ru нечёткий: по запросу «машинное обучение» лента вернула «Дизайнер
  машинной вышивки Wilcom» — вышивальную машину. Поэтому `is_ai_job_theme()`
  требует признак ИИ/ML из `JOB_AI_MARKERS` или `JOB_AI_SHORT`; технического
  слова («разработчик», «инженер», «дизайнер») недостаточно. Короткие формы
  (`ml`, `ds`, `ai`, `ии`) ищутся отдельным словом, иначе «ml» находится в
  «html». Сокращение `cv` намеренно не считается признаком ИИ — в вакансиях
  CV это резюме.

### Блок-слова: заголовок и описание — разные списки

Правило «не наша профессия» работает по двум спискам, и это не дублирование:

| Список | Где ищется | Что внутри |
|---|---|---|
| `JOB_BLOCK_PROFESSIONS` | **заголовок** | полный: продажи, менеджеры, HR, маркетинг, бухгалтеры, юристы |
| `JOB_BLOCK_IN_DESC` | **описание** | узкий: курьер, грузчик, уборщик, кассир, машинист |

**Почему нельзя одним списком.** В описании те же слова значат другое.
Проверено журналом отказов 18.09.2026: «Аналитик-инженер по машинному
обучению» отсеивался из-за слова **«водитель»** (в требованиях были
водительские права), «AI-тренер для обучения нейросетей» от Яндекса — из-за
слова **«контент»**, «ML-инженер (Python · PyTorch · fine-tuning)» — тоже.
Профессия указывается в заголовке; в описании она превращается в обычное слово.

**Латинские названия продублированы кириллицей.** В списке стояли «smm»,
«seo», «marketing», а в русских заголовках пишут «СММ-специалист»
и «Специалист по интернет-маркетингу» — правило их не видело, и обе вакансии
попадали в рубрику.

**«маркетинг» и «реклам» из списка убраны намеренно** — они ловят отрасль,
а не профессию. Из-за них отсеивались «ML-инженер/инженер по машинному
обучению (рекламные технологии)» и «Data Scientist (Маркетинг)»: в скобках
указана отрасль компании, а не род занятий. Вместо широких слов стоят узкие
«интернет-маркетинг» и «по рекламе».

**«обучение» убрано из `JOB_EDU_MARKERS`.** В ИИ-домене это ключевое слово
(«обучение модели», «обучение нейросетей»), а не маркер курса. Из-за него
терялись «Разработчик AI / RAG», «Старший специалист по разметке данных»
и «Старший научный сотрудник» — во всех трёх речь шла об обучении моделей.
Курсы отсеиваются по «курс», «школа», «вебинар», «стажировка» — они есть
в заголовках таких объявлений.

**Замер правки** (датасет 207 уникальных вакансий с живых лент, 18.09.2026):
проходило 98, стало 105. Весь прирост — на «Работе России» (24 → 31);
по hh.ru результат не изменился (74 из 112), там ложных срабатываний
на этой выборке не было.

Из добавленных до сайта дошли две — «Старший специалист по разметке данных»
и «AI-тренер для обучения нейросетей» (Яндекс Крауд). Остальные офисные
и отсеиваются раньше, по полю `employment`: рубрика только для удалёнки.
Мусора не добавилось ни одного, а двое, наоборот, ушли: «Бухгалтер
в SpeShu.AI» и «Специалист по внутренним коммуникациям».

Метод: датасет сохраняется в `_backup/jobs_dataset.json`, варианты правил
сравниваются на нём — по сети «до и после» нечестно, лента отдаёт разное
от запуска к запуску. Важный нюанс: в датасет формат работы не пишется,
поэтому по «Работе России» он показывает верхнюю границу — сколько вакансий
правило пропустило бы, если бы все они были удалёнными.

**Как проверить, что вакансия действительно удалённая** (`check_jobs.py`):
формат читается прямо со страницы вакансии из служебного элемента
`data-qa="work-formats-text"` — там строка вида «Формат работы: удалённо»,
«Формат работы: на месте работодателя» или «Формат работы: на месте
работодателя, удалённо или гибрид». Удалённой считаем ту, где есть «удалён».

**Ловушка:** искать по HTML слова «Удалённо», «Гибрид», «Полный день»
бесполезно — они лежат в справочнике интерфейса и есть на **каждой** вакансии,
включая офисные. Нужен именно атрибут `data-qa="work-formats-text"`.

**Закрытость вакансии по странице определить нельзя.** Строки «Вакансия
закрыта» и `vacancyArchived` тоже есть на каждой странице, включая открытые.
Проверено сравнением открытых вакансий из живой ленты с заведомо закрытыми.
Поэтому `check_jobs.py` закрытость не проверяет — только формат и правила.

Раньше здесь был другой метод — два запроса к ленте hh.ru по заголовку вакансии
(без фильтра и с `schedule=remote`). Он работал, но был косвенным, требовал до
10 запросов на вакансию и смешивал закрытые вакансии с непроиндексированными.

```bash
python check_jobs.py            # отчёт, ничего не меняет
python check_jobs.py --apply    # переписать data/jobs.json (с копией в _backup/)
```

**Заказы** приходят только с FL.ru (`fetch_fl_orders`). Отдельная особенность:
заказ на **сайт** проходит даже без упоминания ИИ — веб-разработка это
самостоятельное направление рубрики (`SITE_MARKERS`). Подкатегории задаёт
`classify_order()`: Сайты, Промты, AI-разработка, Изображения, Видео и аудио,
Автоматизация.

## Служебные файлы сайта

Кроме страниц рубрик сборка кладёт в `docs/` пять файлов, которых раньше
не было. Все они собираются из того же `filtered`, что и рубрики — отдельного
источника правды не заводим, иначе они разъедутся с сайтом.

| Файл | Кто делает | Зачем |
|---|---|---|
| `sitemap.xml` | `render.generate_sitemap()` | все адреса сразу: перелинковки у нас нет, и глубже главной робот не уходит |
| `robots.txt` | `render.generate_robots()` | разрешает обход и указывает карту сайта |
| `rss.xml` | `render.generate_rss()` | своя лента: собираем 36 чужих RSS, а своей не отдавали |
| `search-index.json` | `render.generate_search_index()` | данные для поиска по архиву — фильтрует браузер посетителя |
| `og-image.png` | `copy_static()` | копия из корня проекта — `docs/` целиком генерируется |

### Поиск по сайту

Сервера у сайта нет, поэтому искать нечем: страница рубрики знает только свою
рубрику, а главная — одни счётчики. Решение — один файл со всеми записями
архива рядом с главной; фильтрует его браузер посетителя.

**Поле поиска живёт только на главной.** В шаблон рубрики его не ставили
намеренно: шаблон один на восемь страниц, и любая ошибка разъехалась бы сразу
по всем. Если понадобится и там — это отдельная правка с проверкой.

**Индекс читается лениво** — только когда посетитель ввёл два символа.
На открытие главной он не влияет: сама страница весит 13 КБ, индекс — 576 КБ
(1631 запись), и он запрашивается отдельно.

**Описания обрезаны до 90 знаков** (`SEARCH_DESC_LIMIT`). Замер 18.09.2026:
без описаний индекс весил бы 388 КБ, при 90 знаках — 575 КБ, при полных
300 знаках — около 850 КБ. Длинные описания дают поиску мало, а файл
раздувают вдвое. Если индекс перерастёт `SEARCH_INDEX_WARN_KB` (800 КБ),
сборка напечатает предупреждение: пора разбивать по датам.

**Выдача экранируется тем же `esc()` и `safeUrl()`**, что и карточки рубрик.
Это вторая копия этих функций — общего файла скриптов у сайта нет, и связывать
страницы лишним запросом ради двух функций не стали. Правишь одну — проверь
вторую (тест `test_search_escapes_output` следит за вызовом `esc()` в выдаче).

### Журнал отказов

Фильтры строгие, и у строгости есть цена: хороший материал может пропасть
молча. В логе сборки раньше было только «отброшено N» — по такой строке нельзя
понять, правильно сработали правила или нет. Однажды так и вышло с рубрикой
«Вакансии»: заголовок приходил пустым, записи отбрасывались, а источник
выглядел рабочим.

Теперь каждый отказ записывается в `data/rejects.json` (в git, рядом
с накопителями):

| Что внутри | Зачем |
|---|---|
| `last_run` | сводка за текущий прогон: сколько и за что отсеялось |
| `by_reason`, `total_rejected` | то же накопительно, по всем прогонам |
| `items` | уникальные отказы: заголовок, источник, причина, ссылка, счётчик и даты |

**Записи дедуплицируются по «заголовок + причина».** Ленты отдают одни и те же
материалы шесть раз в день; без дедупликации журнал превратился бы в ленту
повторов. Вместо этого у записи есть `count` и даты первого и последнего отказа.

**На причину — квота** (`MAX_PER_REASON`, 60 записей), общий потолок — 400.
Причины очень разного веса: «нет признака ИИ» за один прогон даёт больше двух
тысяч записей, а «не ИИ-профессия (слово в описании)» — девятнадцать. Без квоты
частые причины вытесняют редкие, и из журнала пропадает ровно то, ради чего он
заведён. Соблюдение квоты проверяет `test_rare_reason_survives_next_to_common_one`.

**Причина называет то, что сработало.** Для вакансий их шесть: «вакансия
на английском», «не сказано про удалёнку», «нет признака ИИ или ML»,
«не ИИ-профессия» (слово в заголовке), «не ИИ-профессия (слово в описании)»
и «курсы или обучение». Плюс отдельная причина «не удалённая работа» у «Работы
России»: там формат сообщает само API, и отказ происходит ещё до фильтра.
Разделение на заголовок и описание — не придирка:
замер 18.09.2026 показал, что по словам **в описании** отсеиваются профильные
вакансии. У «Аналитика-инженера по машинному обучению» в требованиях были
«водительские права», у «Главного специалиста по обучению нейросетей» —
слово «обучение» (и оно же ключевое в ИИ-домене). Помета «(слово в описании)»
выводит такие случаи наверх.

**Проверить конкретную новость:**

```bash
python why.py рачки            # есть на сайте или отсеяна — и почему
python why.py                  # сводка по причинам отказов
```

`why.py` ничего не меняет — только читает архив и журнал.

**Причины живут в `news/filters.py`** (`ai_reject_reason`, `job_reject_reason`,
`order_reject_reason`), а сами фильтры стали их обёртками:
`is_ai_relevant()` — это `ai_reject_reason(...) is None`. Так причина не может
разойтись с решением — это проверяет `tests/test_rejectlog.py`, класс
`TestReasonsMatchFilters`.

### Превью ссылки (Open Graph)

Мессенджер собирает карточку **не из страницы**, а из меток в `<head>`:
JS он не выполняет, текст не читает. Нет меток — видна серая строка адреса.
Метки стоят в шаблоне рубрики, на главной и в `about/index.html`.

**Адреса только абсолютные.** Сайт живёт в подпапке `/ai-news/`, поэтому
`og-image.png` мессенджер не найдёт — нужен `SITE_URL + "/og-image.png"`.
Адрес задан константой в `news/config.py`: смена домена — правка в одном месте.

**Описание у каждой рубрики своё** — `CATEGORY_DESCRIPTIONS`. Общий текст
на всех рубриках выдаёт, что описание забыли.

**Картинка только растровая** (1200×630): SVG и `data:`-адреса не принимает
ни Telegram, ни VK. Скриншот страницы не годится — пропорция 1.6:1, и
мессенджер обрезает его по центру, срезая ровно шапку с названием; плюс
в кадре застывают счётчики и время сборки, а сайт пересобирается 6 раз в день.
Поэтому нарисована чистая карточка без цифр и даты — она не устаревает.

**Подпись на картинке сверяется тестом** с `SITE_TAGLINE`: текст на картинке
запечён в пиксели и не меняется вместе со страницами. На сайте «шесть раз
в день», на карточке «6 раз в сутки» — число одно, а заметит это человек.
Меняешь подзаголовок — перерисуй картинку и прогони тесты.

**Сторож на подстановки.** `generate_category_page()` падает, если в готовой
странице осталась подстановка вида `%%ИМЯ%%`: добавили в шаблон, забыли замену
в сборщике — и посетитель видит этот текст прямо на странице.

## Безопасность

Проект публикует чужие заголовки и ссылки. Сам текст брать можно — мы агрегатор,
а не редакция. Опасность в другом: заголовок из чужой ленты попадает в разметку,
и если в нём приедет тег, браузер посетителя выполнит его как код. Это не про
авторские права, а про то, что чужой текст становится нашей программой.

Проверено 16.09.2026. Тогда дыра была открыта: карточки собирались строкой
и вставлялись через `innerHTML` без экранирования, а заголовок и ссылка шли
из лент как есть.

### Что сделано (два эшелона)

| Где | Что |
|---|---|
| `_category_template.html` | `esc()` для заголовка, источника и даты; `safeUrl()` для ссылки |
| `news/util.py` | `strip_html()` — чистит заголовок от разметки; `safe_link()` — только `http`/`https` и без кавычек |
| `news/fetch.py` | очистка применяется в `_build_item()`, `fetch_fl_orders()`, `fetch_hh_vacancies()`, `parse_trudvsem()` |
| `news/fetch.py` | проверка сертификата TLS включена, размер ответа ограничен `MAX_FEED_BYTES` |

Второй эшелон нужен потому, что шаблон рубрики — ручной файл: при следующей
правке вёрстки вставку легко вернуть «как было». Даже тогда в архив уже
не попадёт запись с тегом в заголовке.

### Правила, которые нельзя нарушать

1. **Всё, что идёт в `innerHTML`, проходит через `esc()`.** Строка 164 шаблона
   собирается конкатенацией — здесь это обязательно. `n.title`, `n.source`,
   `n.date` — все через `esc()`, `n.link` — через `esc(safeUrl(...))`.
   То же правило для выдачи поиска на главной: `it.title`, `it.source`,
   `it.desc` — через `esc()`, `it.link` — через `esc(safeUrl(...))`.
   Сообщения о числе найденных и о пустом результате идут в `textContent`,
   а не в разметку: туда попадает строка запроса, введённая посетителем.
2. **Ссылка — только `http`/`https`.** `javascript:` выполнится по клику.
   Плюс отсев пробелов, кавычек и угловых скобок: с ними адрес вылезает
   из атрибута `href`.
3. **Не отключать проверку сертификата.** Здесь стояли `check_hostname = False`
   и `verify_mode = CERT_NONE` — шифрование было, а подлинность сервера нет.
   Проверено: все 36 лент и три кадровых источника проходят нормальную
   проверку, отключать её незачем.
4. **Заголовок не обрезать.** `strip_html()` в отличие от `clean_desc()`
   длину не режет: заголовок должен остаться целиком.

Тесты на всё это — `tests/test_safety.py`, включая сторож на шаблон:
он падает, если в строке с `innerHTML` появится поле без `esc()`.

### Токен GitHub

Адрес удалённого репозитория в `.git/config` содержит токен открытым текстом.
Токен — **classic** с правами `repo` и `workflow`, то есть доступ ко всем
репозиториям аккаунта, и он **бессрочный**. В историю коммитов и в `docs/`
он не попадал — проверено.

**Папку с этим `.git` нельзя копировать наружу, выкладывать в архив или
отправлять кому-либо.** `PERENOS.md` предлагает переносить проект вместе
с `.git` — при этом уезжает и токен. Правильное решение — отдельный
fine-grained токен только на `ai-news` со сроком, а доступ хранить
в системном хранилище, а не в файле проекта.

  уже накопленных вакансий по фильтру hh.ru.
- **Вакансии: только про ИИ.** `is_ai_job_theme()` отсекает посторонние
  профессии, которые hh.ru подсовывает нечётким поиском.
- **Починена «Работа России».** Источник молча не давал ни одной вакансии
  из-за неверных имён полей (`title` вместо `job-name`). Теперь читает
  `job-name`, `creation-date`, `employment`, `duty`; разбор вынесен в
  `parse_trudvsem()` и покрыт тестами.
- **Накопитель вакансий вычищен (15.09.2026).** Правило само старые записи
  не трогает — они лежат в накопителе до 90 дней. Проверено 239 записей
  через `check_jobs.py`: убрано 118 (109 не удалённых, 9 не про ИИ),
  осталось 121. Копии — в `_backup/jobs_removed_*.json` и
  `jobs_before_check_*.json`, сумма сходится.

**Важно про порядок.** `check_jobs.py --apply` пишет список, собранный из уже
прочитанного файла. Поэтому после `collect.py` его надо запускать заново, иначе
свежесобранные вакансии будут затёрты. Правильная последовательность:
`check_jobs.py --apply` → `collect.py` → коммит.

**Коммит только с `data/` сборку не запускает** — в `deploy.yml` стоит
`paths-ignore: ['data/**']` (защита от цикла коммитов). Поэтому чистка
накопителя попадёт на сайт только со следующей сборкой: по расписанию
(6 раз в день) или после любого коммита, который трогает не только `data/`.

### Чего сознательно НЕ делаем

- **Не переписываем чужие статьи.** Мы агрегатор, а не редакция. Переписать
  чужой текст и выдать за свой — это и авторское право, и обман читателя.
- **Никаких внешних зависимостей** (`feedparser`, `requests`) — стандартная
  библиотека делает то же самое.
- **Никакого VPS** — GitHub Actions справляется на бесплатном тарифе.
- **Никакой монетизации.**
- **Никакого Telegram-бота** — нужен сервер, токен и номер телефона.
